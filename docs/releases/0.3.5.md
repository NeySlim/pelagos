# Pelagos 0.3.5

A fix for the **Administration > Updates** screen, which answered "Permission denied" on nodes whose Kea was migrated to ISC Kea 3, and a release process where the container images move only when the release is published. Nothing changes in the data of a cluster: an upgrade from 0.3.4 is a package update.

## Fixes
- **Updates screen: "[Errno 13] Permission denied: /var/lib/pelagos-helper/upgrade/packages/0.3.4"**: on a node where the ISC Kea migration had run, the folder of the update helper was left `0750 root:root`. The screen, its **Check now** button and the update status a peer asks for read that folder as the service user and failed with this error instead of showing the updates. These reads now treat a folder they cannot open as holding no release, and the update helper opens the folder for reading (never for writing) the next time it runs; the Kea migration creates it `0755`. Nothing in it becomes writable by the service user.
  - **Staying on 0.3.4 for now?** `sudo chmod 0755 /var/lib/pelagos-helper` on each node makes the screen work again, including an update to 0.3.5 from the screen. The folder stays owned by root and not writable by the service user.

## Release process
- The container images on ghcr.io get their version tag (`0.3.5`) and `latest` only when the GitHub release is published, not while it is a draft. During the draft only the tested candidates `0.3.5-amd64` and `0.3.5-arm64` are pushed; publishing points `0.3.5` and `latest` at those same images without rebuilding them. `latest` only moves for the newest release. `docs/dev/release.md` describes the steps.

## Tested
- **Upgrade 0.3.4 to 0.3.5 with `scripts/deploy-prod.sh`** on an HA pair set up like a production cluster: Debian 13, BIND 9.20, Kea migrated to ISC Kea 3.2.1, HA hot-standby over TLS, `/var/lib/pelagos-helper` left `0750 root:root` by the migration and no update ever made from the screen. On 0.3.4 the Updates screen and **Check now** failed with the "Permission denied" error on both nodes. Both nodes upgraded in 99 s, standby first; a probe asking both nodes for a zone every second got 186 answers out of 186; the pair stayed in hot-standby and Kea and named were not restarted. On 0.3.5 the screen and **Check now** answer on both nodes, the check reaching GitHub without error.
- **Updates from the screen** with the fix, on the same pair: a release sent to both nodes and rolled out from the screen, the previous release kept for a rollback, and a broken release rolled back by itself on the node that took it.
- **Release workflow**: the image promotion replayed against a local registry (amd64 and arm64 images): a draft pushes the candidates only and leaves `latest` alone; publishing points the version tag and `latest` at the candidates' digests; a replaced or missing candidate is refused. The first real run on GitHub is this release.
- Unit, frontend, end-to-end and daemon suites (BIND and Kea running for real).

## Upgrade
- **From 0.3.4**: `scripts/deploy-prod.sh --tag v0.3.5 <standby> <primary>` (or a downloaded release directory in place of `--tag`, docs/user/upgrade.md), or **Administration > Updates** once the screen works (`sudo chmod 0755 /var/lib/pelagos-helper` above).
- **Docker**: `ghcr.io/neyslim/pelagos:0.3.5` and `ghcr.io/neyslim/pelagos-allinone:0.3.5` (amd64 and arm64), available once the release is published.
- **RHEL 9 and 10**: the el9 and el10 rpms are attached to the release.
- This release is **not signed**: the Updates screen shows it as *Not signed* and asks for the extra confirmation. The sums of `SHA256SUMS` are checked in every case.
