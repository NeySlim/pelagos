# Pelagos 0.3.3

Fixes for DHCP changes refused by the permission check when Kea runs under an AppArmor profile that is not one of Kea's own (for instance Docker's `docker-default`), and in the all-in-one image built with Debian's Kea 2.6. Nothing changes in the data of a cluster: an upgrade from 0.3.2 is a package update.

## Fixes
- **DHCP changes refused under a non-Kea AppArmor profile**: the permission check took any AppArmor profile in enforce mode around the Kea daemon for Debian's read-only Kea profile. In the all-in-one Docker image Kea runs under `docker-default` (a site's own profile had the same effect), so every plan that makes Kea rewrite its configuration file (subnets, pools, reservations, options, HA) was refused with "its AppArmor profile (enforce) only lets it read /etc/kea", the alert `path_not_writable` was raised, and the suggested fix pointed at a `usr.sbin.docker-default` file that does not exist. The check now judges only the Kea profiles (`kea-dhcp4`, `kea-dhcp6`, `kea-dhcp-ddns`, `kea-ctrl-agent`) and asks the kernel whether the loaded profile allows the write, so a rule added to the local override counts as soon as the profile is reloaded. On a Debian host with Kea's own profile nothing changes: a configuration file Kea cannot rewrite is still reported, with the rule to add.
- **All-in-one image built with Debian's Kea 2.6** (`make docker-allinone KEA_SOURCE=distro`, not published): Kea 2.6 creates its control sockets 0750, so the node (in the Kea group) could not connect to them and DHCP changes failed with "Permission denied". The image now makes the sockets group-writable after Kea starts, as the packages do on a host. The published image (ISC Kea 3.2) was not affected.

## Documentation
- README: the current version comes from a release badge instead of a fixed number; the rpm is built from the repository; the container images are published to ghcr.io with each release.

## Tested
- **Upgrade 0.3.2 to 0.3.3 with `scripts/deploy-prod.sh`** on an HA pair reproducing a production cluster: Debian 13, BIND 9.20, Kea migrated from 2.6.3 to ISC Kea 3.2.1, HA hot-standby over TLS, nodes naming their interface differently, a DHCP client renewing every 3 s during the whole upgrade. Both nodes upgraded in 99 s, the pair stayed in hot-standby, Kea and named were not restarted, the permission check found every path writable before and after, the client got 110 answers out of 110 (no NAK, longest gap 1.0 s), zones served, sign-in and screens answering, a new lease seen on both nodes afterwards.
- **Mixed pair amd64 and arm64 (emulated)**, Kea 2.6.3 from Debian in HA: 0.3.2 to 0.3.3 with `scripts/deploy-prod.sh`. Both nodes upgraded (arm64 standby first), hot-standby kept, Kea not restarted, zones served, sign-in working.
- **Docker**: node and all-in-one images built from the release commit, compose and all-in-one smoke tests, both Kea sources of the all-in-one image (ISC 3.2.1 and Kea 2.6.3). The all-in-one smoke test now imports the bundled engines and applies a DHCP subnet plan that Kea writes back to its configuration file, on a host with AppArmor enabled (Kea under `docker-default`): refused with the 0.3.2 image, applied with 0.3.3 for both Kea sources.

## Upgrade
- **From 0.3.2**: `scripts/deploy-prod.sh <release dir> <standby> <primary>` (docs/user/upgrade.md), or **Administration > Updates**.
- **Docker**: `ghcr.io/neyslim/pelagos:0.3.3` and `ghcr.io/neyslim/pelagos-allinone:0.3.3` (amd64 and arm64).
- **RHEL 9 and 10**: the el9 and el10 rpms are attached to the release.
- This release is **not signed**: the Updates screen shows it as *Not signed* and asks for the extra confirmation. The sums of `SHA256SUMS` are checked in every case.
