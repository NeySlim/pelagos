# Zones: static and dynamic, views, added zones, catalogs, DNSSEC

How Pelagos writes each kind of zone, and what it means for the operator.

## Dynamic and static zones

A primary zone with `allow-update` or `update-policy` is **dynamic**: record
changes are signed DNS UPDATEs (`ddi-admin`, or the view's key). named keeps
them in a journal (`<file>.jnl`) and rewrites the zone file from time to time.

A primary zone without either (or with `allow-update { none; }`) is **static**.
Pelagos does not change that: a record change edits the zone file itself, on
the node that holds it.

- Only the lines of the records that change are touched. Comments, blank
  lines, `$ORIGIN`, `$TTL` and `$INCLUDE` stay as written; a record that lives
  in an included file is edited in that file. When a removed line gave its
  owner or TTL to the next record, that record gets them written out.
- The SOA serial is bumped in the zone's own scheme: a `YYYYMMDDnn` serial moves
  to today (or counts up within the day), any other serial is incremented.
- The edit is checked with `named-checkzone` on a copy, written atomically
  (owner, mode and SELinux label kept, backup kept), then `rndc reload <zone>`
  loads it and named sends NOTIFY to the secondaries.
- Rollback writes the inverse edit with a new serial, so the secondaries
  transfer the restored records.
- The plan preview shows the zone file diff and says "file edit, the zone
  stays static". If the Pelagos service cannot replace the file (file or
  directory not writable), the plan fails and says which file and why.
- Records generated by `$GENERATE` are kept but cannot be edited.

### Converting a static zone to dynamic

The security audit reports every static zone (`static_zone`, info) except the
zones the distribution ships (localhost and the reverse zones of 127, 0 and
255). Its remediation replaces `allow-update { none; }` by, or adds,
`update-policy { grant ddi-admin zonesub ...; };` (the view's key in a view).
After the conversion:

- named records changes in `<file>.jnl` next to the zone file, so that
  directory must be writable by named (the remediation refuses otherwise:
  on Debian, zone files under `/etc/bind` usually move to `/var/lib/bind`).
- named rewrites the zone file itself; comments and formatting are lost at
  the first rewrite.
- To edit the file by hand: `rndc freeze <zone>`, edit (bump the serial),
  `rndc thaw <zone>`. Editing it while the zone is thawed loses the change or
  breaks the journal.

## Views

When the configuration has two views or more, the key of a request decides
which view answers it. The audit finding `view_key` proposes, for each view:
a key `ddi-<view>`, `key ddi-<view>;` first in that view's `match-clients`,
`!key ddi-<view>;` first in the `match-clients` of the views before it, and
grants and transfer rights for that key on the view's zones. Clients matched
today keep their view: only requests signed with the new key move. Views
selected by `match-destinations` or `match-recursive-only` are not rewritten;
check them after the change. The key is stored as
`settings.dns.view_keys.<view>` in `cluster.toml`; reads, record plans and AXFR
in that view use it, and the zone page offers a view selector when a zone
exists in several views.

## Zones added with rndc addzone

Zones named loaded from `rndc addzone` (kept in `<view>.nzd`, or `.nzf` when
named is built without LMDB) are listed with the source `rndc addzone`. They
are changed with `rndc modzone` and removed with `rndc delzone` (the zone file
is kept); a new zone can be added that way too when `allow-new-zones yes;` is
set. Rollback runs the inverse command.

## Catalog zones

Consumed catalogs come from `catalog-zones` statements; produced catalogs are
primary zones whose `version` TXT record names a catalog schema. Members are
read from the catalog zone content. On a producer, adding a member writes the
PTR record `<sha1 of the member name>.zones.<catalog>` (and its `group` TXT
property) like any record change; the consumers pick it up by transfer.

## DNSSEC

`dnssec-policy` statements live in `policies.conf` of the include directory;
their statements are checked against the BIND grammar. A policy is attached
from the zone edit form (`dnssec-policy`, `inline-signing`). Key rollovers
(`rndc dnssec -rollover`) and the parent's DS state (`rndc dnssec -checkds
published|withdrawn`) are plans that ask for confirmation and cannot be rolled
back. The DNSSEC page shows the DS of each KSK or CSK and whether the parent
must publish or withdraw it.
