Reading needs `read:dns`; each write names its permission. Background on
how each kind of zone is written: [Zones: static and dynamic, views,

## Zones

Every zone of every view, from every node, with:

- **Type**: Primary, Secondary, Stub, Static stub, Forward, Mirror, Hint,
  Redirect.
- **Source**: Existing config (your `named.conf`), Pelagos (its include
  directory), Catalog (a member of a consumed catalog), rndc addzone (kept
  by named in its NZD database).
- **Serial per node** and **Sync**: the SOA serial each node serves. A
  node behind the highest serial is highlighted; the zone counts as
  Divergent until the secondaries catch up (`serial_divergence` alert after
  `alerts_serial_divergence_seconds`).
- **Mode**: Dynamic or Static (below).

The counters on top give the totals: zones, primary, secondary, divergent,
static. "Resynchronize" on a lagging zone asks its secondaries to
retransfer.

### Add a zone

"Add zone" (`write:dns.zones`) builds a zone plan:

- **Primary**: the zone file is proposed under the Pelagos zone directory
  (`/var/cache/bind/pelagos` on Debian, `/var/named/pelagos` on RHEL) with
  a minimal SOA and NS. "Name servers (NS)" is prefilled from the nodes
  running BIND: the host name of each node's URL when it has a domain, else
  `<node name> <address>`. One line per server: a full name
  (`ns1.example.lan.`), or a name in the new zone with its address
  (`ns1 192.0.2.53`, which also adds its A or AAAA record, as BIND needs
  for a name server inside its own zone). Left empty, the plan uses the
  `dns.default_ns` setting; with neither, or with `localhost.`, the plan
  is refused. Unless you give them, Pelagos adds
  `update-policy { grant ddi-admin zonesub ANY; };` and
  `allow-transfer { key ddi-read; };`, so the zone is dynamic and readable.
  Tick other nodes under "Also on these nodes, as secondaries" to create the
  secondaries in the same plan, as many as the cluster has; their primaries
  default to this node's addresses with `key ddi-read`, and the primary's
  `also-notify` names every one of them.
- **Secondary**, **Stub**, **Mirror**, **Redirect**: one primary per line
  (`192.0.2.11 key ddi-read`). Mirror without primaries is allowed for the
  root zone only.
- **Static stub**: server addresses or server names.
- **Forward**: forwarders and forward mode.
- **Hint**: the root hints file, for example `/usr/share/dns/root.hints`.
- "Add with rndc addzone": the zone goes to named's NZD database instead of
  `zones.conf` (needs `allow-new-zones yes;`). Such zones are changed with
  `rndc modzone` and removed with `rndc delzone`.

## A zone

Click a zone to open it. Tabs:

- **Records**: the record sets read from the zone (AXFR with `ddi-read`),
  with search, the serial they were read at and the node read. On a primary
  you can add, edit and delete record sets (`write:dns.records`) of types
  A, AAAA, CNAME, MX, TXT, SRV, PTR, NS, CAA and DHCID. The editor checks
  each value (IPv4, IPv6, host names, `preference host` for MX, `priority
  weight port target` for SRV, `flags tag "value"` for CAA, quoted strings
  of at most 255 characters for TXT) and shows the before and after; "Preview
  the plan" builds the plan. Records generated by `$GENERATE` are kept but
  not editable.

  For A and AAAA, **Create or update the PTR** puts the reverse records in
  the same plan (same preview, apply and rollback). It is checked when a
  reverse zone served by the cluster covers the address, and greyed out
  with the reason otherwise (no reverse zone, or a secondary copy whose
  primary no node can reach). When an address changes, the old PTR is
  removed and the new one written; deleting an A or AAAA offers **Also
  delete the PTR that points to this name**. A PTR that already names
  another host is shown in the editor and replaced only for an address the
  record set did not have: the plan then asks for confirmation and its
  checks name the old target. A kept address whose PTR names another host
  is left alone. With views, the PTR goes to the same view as the records,
  as in the host plan. In a record set of several addresses, each address
  gets its own PTR, and a PTR naming several hosts keeps the others.
- **Status per node**: SOA serial, loaded serial, last loaded, next
  refresh, expiry and files, as `rndc zonestatus` reports them on each node
  holding the zone. On a primary with secondaries, a row per secondary
  shows the transfer from the primary (a bar runs when that node catches up
  to a new serial) and whether it is in sync, and "Secondary nodes" sets
  which nodes hold a copy (below).
- **Configuration**: the zone statement (file, primaries, `allow-transfer`,
  `allow-update`, `update-policy`, `also-notify`, DNSSEC policy, other
  statements) and where it is declared.

Actions (`ops:dns` for the rndc ones):

- **Notify**, **Reload**, **Retransfer** (secondaries) on the node you pick.
- **Edit zone** (`write:dns.zones`, zones of source Pelagos or rndc addzone
  only): primaries, `also-notify`, `allow-transfer`, `update-policy`,
  `allow-update`, forwarders and forward mode, DNSSEC policy, inline
  signing, a note. A zone declared in your own files says "Defined in a
  user file: edit it in named.conf" (use the
  [named.conf editor](screens.md#advanced) or your editor).
- **Delete zone**: a confirmed plan; "Also remove the secondary copies on"
  removes the secondaries Pelagos created on the other nodes.
- **Convert to dynamic** (static zones): builds the `static_zone` security
  remediation for this zone (below).
- **DNSSEC**: opens the DNSSEC page of the zone.

When a zone exists in several views, a view selector switches between
them.

## Static and dynamic zones

- **Dynamic**: the zone has an `update-policy`, or an `allow-update` that
  permits something. Record changes are DNS UPDATE messages signed with
  `ddi-admin` (or the view's key), sent to the primary; BIND writes its
  journal and bumps the serial, the secondaries transfer. Never edit the
  file of a dynamic zone while `named` runs: `rndc freeze <zone>`, edit
  (bump the serial), `rndc thaw <zone>`.
- **Static**: neither. Pelagos edits the zone file itself on the node that
  holds it: only the lines that change (comments, `$ORIGIN`, `$TTL`,
  `$INCLUDE` kept), serial bumped in the zone's own scheme,
  `named-checkzone` on a copy, atomic write, `rndc reload <zone>` with
  NOTIFY. The plan says "file edit, the zone stays static". The
  `pelagos` user needs write access to the file and its directory: see
  [Troubleshooting: permissions](troubleshooting.md#permissions-on-zone-and-kea-files).

**Converting**: the security audit lists every static zone
(`static_zone`, info), except the distribution's own zones. Its
remediation replaces `allow-update { none; }` by, or adds,
`update-policy { grant ddi-admin zonesub ...; };`, after checking that
named can write the journal (`<file>.jnl`) next to the file. Afterwards
named rewrites the file itself: comments and formatting are lost at the
first rewrite. On Debian, zone files under `/etc/bind` usually move to
`/var/lib/bind` first.

## Views

With two views or more, the key of a request decides which view answers
it. The `view_key` remediation gives each view its own key `ddi-<view>`:
`key ddi-<view>;` first in that view's `match-clients`, `!key ddi-<view>;`
first in the views before it, grants and transfer rights for that key on
the view's zones. Clients matched today keep their view. The key name is
kept in `settings.dns.view_keys`; reads, record plans and transfers in that
view use it, and zone pages show the view selector.

## Resolver

Recursion (`recursion`, `allow-recursion`), forwarders (address, optionally
`port N`), forward mode (BIND default `first`, or `only`), DNSSEC validation,
and forward zones. "Per node" shows each node's values and flags those that
differ. Changes (`write:dns.config`) go to the Pelagos `options.conf`; an
option already set in your own files is not editable here until you hand it
over (see "Hand over to Pelagos" below).

## ACLs and keys

- **ACLs**: address match lists managed in `acls.conf`. Elements are
  addresses, prefixes, ACL names or `key <name>`. Built-in names (`any`,
  `none`, `localhost`, `localnets`) are reserved.
- **TSIG keys**: name, algorithm, where it is defined and what uses it.
  "Add key" generates the secret when you leave it empty. "Reveal"
  (`read:dns.secrets`) shows a secret and writes an audit entry. "Rotate
  the secret" (and "switch to hmac-sha256" for a weak key) is a confirmed
  plan: every peer using the key needs the new secret at the same time.
  For the key shared with Kea D2, use the security audit, which switches
  both sides without losing an update.

## Hand over to Pelagos

An option, ACL, key or zone declared in your own `named.conf` files is shown
as `User file` and Pelagos only reads it. A "Hand over to Pelagos" card
lists them on the Resolver screen (options), on each tab of ACLs and keys,
and on the Zones screen (zones); a zone also has "Hand over the zone" in its
header. "Hand this option over to Pelagos" (or ACL, key, zone) acts on one
statement, "Hand over all" on the whole screen. Nodes that have the same
statement are handled in the same plan. The plan is built on the node you are
connected to, so only statements that node has are offered: one that exists
only on a peer must be handed over from that peer. A node that no longer has
a statement (already moved) is skipped when the plan is applied.

One plan does everything: the statement is removed from your file, replaced
by a `# moved to options.conf by Pelagos` comment (the rest of the file is
kept byte for byte), and written with the same value to `options.conf`,
`acls.conf`, `keys.conf` or `zones.conf` (`views/<view>.conf` for a zone in a
view). The preview shows both files, `named-checkconf` validates the result,
and after `rndc reconfig` the effective value printed by `named-checkconf -p`
must be what it was; otherwise the files are restored. Secrets stay masked in
the preview. The zone can then be edited on its screen. Comments inside the
moved zone, ACL or key are lost: the text that moves is the canonical form of
the statement (comments around it stay in your file). A handed-over key is
written to `keys.conf` only; it is not added to the cluster secret store, so
cluster-wide rotation and replication of its secret are your job until you
rotate it from the Keys tab. Not offered: the `directory` option, an option
set several times (such as `listen-on`), keys declared inside a view, and the
rndc control keys (`rndc.key`, `rndc.conf` or any key named by a `controls`
statement), because `rndc` and named read them from their own files. An option that must stay in your file (for example
because another tool owns it) is simply left alone.

## Secondaries

Secondary, stub and mirror zones with their primaries, last refresh,
expiry and errors. A secondary or mirror zone that expires within 24 hours
raises `secondary_stale`. "Retransfer" forces a new
transfer from the primary.

### Several secondaries

A primary may have any number of secondary nodes. On the zone's "Status per
node" tab, "Secondary nodes" lists every node running BIND except the
primary, the current secondaries ticked; tick or untick, then "Plan the
secondaries" (`write:dns.zones`, confirmation when a copy is removed). The
plan has one part per node:

- on the primary, the zone's `also-notify` becomes the addresses of the
  ticked nodes (addresses that are not cluster nodes are kept);
  `allow-transfer` already grants `key ddi-read`, which every node shares;
- on each node ticked, a secondary of the primary (`primaries` the
  primary's address with `key ddi-read`, the same `allow-transfer` so
  Pelagos reads the copy);
- on each node unticked, the copy is removed.

The API (`POST /dns/zones/{zone}/secondaries/plan`) also takes `primaries`
and `also_notify` when named listens elsewhere than the address of the
node's replication URL. A zone declared in your own files keeps its
`also-notify` as written: add the new secondaries there.

A record plan is applied on the primary (from any node); the secondaries
follow by NOTIFY and IXFR, and `serial_divergence` is raised for the one
that stays behind. Catalog zones are another way to spread zones to many
secondaries: each consumer node picks up the members by itself.

## DNSSEC

- **Keys** per signed zone: tag, role (KSK, ZSK, CSK), state, published,
  next rollover, next re-signing, read on which node.
- **DS records for the parent zone**: the DS of each KSK or CSK, and what
  to do at the parent: "publish this DS at the parent zone, then confirm with
  DS published", or withdraw it.
- **Roll over**, **DS published**, **DS withdrawn**: `rndc dnssec
  -rollover` and `rndc dnssec -checkds published|withdrawn`, as confirmed
  plans that cannot be rolled back (`write:dns.zones`).
- **Policies**: the `dnssec-policy` statements of `policies.conf` (one
  statement per line, checked against the grammar), the built-in `default`,
  `insecure` and `none`, and the zones using each. A policy is attached to
  a zone from Edit zone (DNSSEC policy, inline signing).

## RPZ

The RPZ screen has four tabs. **Subscriptions**, **Exceptions** and
**Activity** manage public block lists and are described in
[RPZ block lists](rpz.md). **Policy zones** shows the response policy zones
of the `response-policy` statement with their policy and rule count; the ones
you declared in `named.conf` (or with the named.conf editor) have their
records edited like any zone, the ones Pelagos creates for subscriptions are
listed as "subscription".

## Catalog zones

Consumed catalogs (from `catalog-zones` statements) and produced catalogs
(primary zones with a `version` TXT record), with their schema version,
members and groups. On a producer, "Add member" and "Remove" are record
plans (`write:dns.records`): the PTR `<sha1 of the member>.zones.<catalog>`
and its `group` property; the consumers pick it up by transfer. Members of
a consumed catalog are managed on its producer.

## Instances

One card per node running BIND: running or stopped, version, start time,
uptime, configuration load time, memory, `rndc status`, a live query rate,
and the statistics channel counters (queries, responses, recursive
queries, dynamic updates and failures, transfers, DNSSEC validations and
failures, response codes, query types). "No statistics channel" means the
import did not find or add one: run `pelagos import` again.

## Orphan PTRs

**DNS, Orphan PTRs** lists the PTR records whose target has no A or AAAA
to their address, in every reverse zone the cluster serves:

- **Orphan**: the target is in a zone Pelagos manages and does not have
  this address. The fix shown is **Create the A** (or AAAA) when the target
  has no address of that family at all, **Delete** otherwise.
- **External target, not verifiable**: the target is outside every managed
  zone; Pelagos cannot tell whether it is right.
- **Ignored**: the admin chose to keep it (below).

A **DDNS** badge marks a PTR written by Kea (a DHCID sits next to it); its
lease column shows when the client was last seen, or that the lease is
gone. **Delete** works on one row or on the selected rows: one plan,
previewed, confirmed and rolled back as any record plan (`write:dns.records`).

**Ignore** keeps a PTR as it is on purpose: see
[Consistency exceptions](screens.md#consistency-exceptions).
